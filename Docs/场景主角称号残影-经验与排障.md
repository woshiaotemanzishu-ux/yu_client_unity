# 场景主角称号残影：经验与排障

> 状态：已修复并通过专项回归
>
> 最后核对：2026-08-06
>
> 适用范围：`SceneController`、`SceneManager`、`SceneDesignationPresenter`、`DesignationWearSceneCase`

## 1. 故障表现

主角头顶称号正常跟随移动，但进场位置还留有一份相同的静态称号。静态称号不会随主角更新，切场景或清场前一直存在。以称号 `801001 / 海域之王` 为例，现场可同时看到两份完全相同的图片。

这不是 RenderTexture 没有清帧，也不是同一个 `NameBoard` 的坐标刷新失败。修前专项明确发现两个对象：

- `MainRoleDesignation`：读取 `RoleModel.X/Y`，会跟随主角。
- `RoleDesignation_<主角ID>`：读取进场 `RoleVo.X/Y`，主角本地移动时该快照不再更新，所以停在出生点。

修前回归日志为 `noDuplicateMain=False / stationaryGhostObserved=True`。

## 2. 根因

`12002/12003` 的角色块会包含主角自身。老端 `h5/src/scene/SceneManager.ts` 的 `CreateRole` 在命中主角 ID 后执行 `_mainrole_vo.ChangeFromVo(role_vo)` 并立即 `return`；本项目战斗代码也明确依赖“主角不在 `_roles`”。因此主角只更新主角模型，不进入 `SceneManager._roles` 的“其他玩家表”。

旧实现虽然在 `SceneController.ParseRole` 中识别了主角并同步 `PkStatus`，但同步后没有结束分支，仍无条件调用 `SceneManager.AddRole(vo)`。`SceneDesignationPresenter` 又同时消费两条数据源：

1. `RoleModel` 创建 `MainRoleDesignation`；
2. `SceneManager.AllRoles` 为每个 `RoleVo` 创建 `RoleDesignation_<id>`。

于是主角被创建两次。`SceneController.On12001` 对主角移动包会按本地推进规则提前返回，第二份 `RoleVo` 的进场坐标不会改变，最终表现为静态残影。

## 3. 修复边界

本轮采用数据边界和展示防御两层收口：

1. `SceneController.ApplyParsedRole` 遇到主角 ID 时只同步 `PkStatus` 并立即返回，不再写入 `SceneManager`。
2. `SceneDesignationPresenter.RefreshRole` 即使收到历史脏数据或热重载前遗留的主角同 ID `RoleVo`，也会拒绝创建并清理对应普通角色称号。
3. `RefreshMain` 每次刷新主角称号前清理 `RoleDesignation_<当前主角ID>`，使已存在的旧副本无需等切场景即可消失。

没有修改称号图片、动态特效、Prefab、排序层或正常主角称号的跟随公式。

## 4. 后续实现必须保持的约定

- `SceneManager.AllRoles` 表示其他玩家/假人场景对象，不应包含当前 `RoleModel.RoleId`。
- 解析角色快照时，“已识别主角”必须是终止分支，不能只同步字段后继续落普通角色表。
- 所有遍历 `AllRoles` 并创建场景表现的消费者，都应防御性跳过当前主角 ID；不能只相信上游永远干净。
- 回归必须主动构造“主角同 ID 出现在角色快照”这一输入，并在移动主角坐标后同时断言：主称号已移动、普通角色同 ID 称号不存在。
- 对“模型/称号存在但位置残留”类问题，应先统计实例身份和数据源，再排查渲染清帧；不要把两个实例误判成一个实例的 GPU 残影。
