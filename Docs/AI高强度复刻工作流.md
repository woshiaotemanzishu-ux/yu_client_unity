# AI高强度复刻工作流

目标是完整复刻 `D:\GitProject\yu_client` Laya 老客户端到 Unity，不接受“空壳 UI”“本机烟测可见但仓库不可复现”“凭感觉补功能”作为完成。

## 角色分工

- Codex/GPT：技术负责人和验收负责人。负责读老端源码、读 Unity 当前实现、拆任务包、写确认问题、审 diff、决定下一轮优先级。
- Claude Code：实现执行者。只按任务包写代码，不自行扩大到无验收价值的 UI shell。
- 并行只读检查：需要多 agent 时拆成三路，分别查进程/日志、diff/代码风险、验证/问题单。写代码只允许一个 owner 操作同一文件区域。

## 高额度使用方式

- 不以省额度为目标，以减少返工为目标。Claude 持续做实现，Codex 同时准备下一包、查老端、验收上一包。
- 同一轮可并行使用多个只读 agent 做源码抽取、资源可复现检查、运行日志检查。
- 多个写入 agent 只在文件边界清楚时开启，例如资源流水线、进游戏链路、单个 UI 模块分别在不同文件集合内推进；否则会互相覆盖。
- 每个 Claude 任务包都必须包含老端源码路径、Unity 目标文件、禁止做法、验收命令和失败时要回报的证据。

## 每轮流程

1. Codex 做只读盘点：`AGENTS.md` 要求文档、git 状态、最近提交、老端源码锚点、当前 Unity 缺口。
2. Codex 写一份任务包：只交付一个可验收竖切，不给“顺手补一批界面”的开放题。
3. Claude 执行：先修阻塞门，再做可见功能，不得用假数据绕过协议/配置。
4. Codex 验收：看 diff、看资源是否可复现、跑构建/实机 Play 验证、只报告有证据的问题。
5. 通过后更新进度；失败则写下一轮修复包，不把失败包装成完成。

## 验收硬门槛

- 资源可复现：完成项依赖的 prefab、meta、Addressables key 必须能从 clean checkout 复现；本机 ignored/untracked 文件不能算完成。
- 构建通过：至少跑 `dotnet build yu_client_unity.slnx -v:minimal`，Unity 资源变更还要给出 Unity Editor/Play 侧证据。
- 老端对齐：每个行为必须指向 Laya 源码或协议出处。
- 可见进展：优先验收进游戏后能看到、能点、能触发真实数据的主链路，不用 UI 数量冒充进度。
- 禁止 fake/stub：未接协议/配置/资源时要写 blocker，不得填假模型、假 NPC、假任务。

## 主竖切优先级

第一阶段只盯这一条链路：

`选角/创角 -> 10004 -> EVT_GAME_START -> MainUI -> 地图 -> 主角 -> NPC/怪物 -> 任务追踪 -> 点击任务寻路/对话/完成弹层`

验收状态按竖切打分，不按“新增了多少窗口”打分：

- A. GAME_START 门：13001、10201、30005、13088、10202 是否真实齐备。
- B. MainUI：首批 HUD 是否完整显示并由真实 RoleModel/TaskModel/SceneModel 刷新。
- C. 地图：12005、12100、12002 后地图、主角、场景对象是否可见。
- D. NPC：12100/12103/12020 数据是否落表、渲染、头顶任务标是否刷新、能否点击。
- E. 任务：30000/30001 数据是否显示，点击是否进入老端 `DoTask` 等价路径。
- F. 弹层：NPC 对话、任务完成、地图入口等是否从老端入口链打开。

## 本工作流的完成定义

每轮只在以下条件都满足时记为完成：

- 任务包内所有验收项通过，或有明确 blocker 和证据。
- `git status` 中没有新增未解释的资源/生成物污染。
- 如果动 UI/资源，Addressables 和 prefab/meta 的入库/再生成路径被证明。
- `Docs/Shenxiao实施进度.md` 只记录已验证事实，不记录“看起来应该好了”。
