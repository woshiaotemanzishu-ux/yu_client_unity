# 人物与设置面板对标：经验与排障

> 状态：生效  
> 最后核对：2026-08-06

## 1. 适用范围

本文覆盖 `RoleModule/EquipmentView` 与 `SettingModule/SettingView` 的老端对标、动态列表布局、资源复原和功能验收。老端事实源依次为：`http://127.0.0.1:8091/` 运行态、Laya `.scene`、业务 TypeScript；Unity 侧以当前人工接管的可编辑 Prefab 和真实 `BaseView.Show()` 运行态为准。

## 2. 已确认的根因

### 2.1 设置页“整体像错位/错版”

问题不是 652×936 主面板坐标整体错误，而是两类问题叠加：

1. `Assets/GameRes/resource/game/setting/texture` 缺少老端原始图片，且若干同名 PNG 实际内容被错误资源占用。例如 `ui_button_rect8.png` 被导成圆形刷新图，正确资源应是“更换头像”红色横条；`ui_button_rect5.png` 被导成圆形“基本设置”，正确资源应是页签底图。
2. 旧快照把 `change_head_btn` 和 `_btn_copy` 误取成内部小图的结算尺寸。老端 `.scene` 与当前运行态的最终值分别是 `125×37`、`100×34`，文字必须可见。

排查设置页时，应先直接查看 PNG 内容和 `.scene` 的 `skin`，不能只看文件名、GUID 或 RectTransform。

### 2.2 真机上偶发纵向错位

旧实现由 `SettingView.ReflowBaseBlocks`、`PlaceShieldItem` 和 `EquipmentView.EnsureAttrItems` 在运行时写 `anchoredPosition/sizeDelta`。这会让转换坐标、Canvas 缩放和代码二次布局同时生效，编辑器与真机容易出现不同结果。

当前约定：

- 设置页五个动态分块使用 Prefab 内 `VerticalLayoutGroup + ContentSizeFitter`；每个分块放在独立 Row 中，横向偏移由 Creator 固化，运行时只显隐 Row。
- 自动拾取、屏蔽列表和人物属性列表使用 Prefab 内 `GridLayoutGroup + ContentSizeFitter`；运行时只克隆、填数据和显隐。
- 人物战力项由 Prefab 内 `HorizontalLayoutGroup` 居中。
- 禁止在上述 View 的刷新逻辑中重新计算面板坐标。

### 2.3 设置子功能“能打开”但未闭环

2026-08-03 用户完整操作后确认两个漏验收问题；继续沿路由深挖后，又校正了头像页的根因：

1. 改名提交成功后，已打开的设置面板角色名没有立即更新，只有退出重进才看到新名。这说明回包/Model 虽可能已更新，当前 `SettingView` 没有消费对应事件或刷新链。
2. 更换头像可以跳转，但页面加载超过 5 秒，且设置入口落在城楼背景的“发饰”。用户给出的老端截图实际是外层“装扮”里的内层“头像”；老端“发饰”本身也是城楼背景。根因不是整个 Fashion 页面版本过旧，而是 `FashionFlow.Open(1)` 把参数解释为外层页签索引，稳定开错页。
3. 登录阶段释放登录页后，设置里的用户协议/隐私政策仍调用已清空的 `_agreementView`，表现为可点击但无页面。设置侧必须在没有保留实例时通过 `ViewManager.Open<LoginUserAgreementView>`重新加载，不能依赖登录期对象寿命。
4. `FashionMainView.Refresh()`在收到41312战力包后再次无条件请求41312，会形成事件→刷新→请求→回包→事件循环。战力查询必须按“当前复合键无缓存且未在途”去重，配置/染色/升阶改变后只失效受影响键。

排查改名时必须跑完“提交 → 成败回包 → RoleModel → 当前 SettingView 立即刷新 → 重开”；排查头像时必须另外记录 cold/warm 的 `click→first-visible/interactive-ready`，并把老端当前页签、布局、功能库格当成页面身份。资源验收必须先按配置求实际闭包，再比较点击前后的文件、`.meta` 和 Git 状态；首次点击临时导入资源属于失败，不能用“第二次变快”掩盖。

### 2.4 功能绿灯但视觉/状态仍错误

2026-08-04 的用户截图证明：真实点击、协议回包和重开全部通过后，页面仍可能存在模型未出现、套装部件累积、假灰阶、错误红点、战力不刷新或页内状态按钮漏点。设置/时装类页面必须拆成四层验收：功能、真实运行态、视觉、性能。

- 2D 的位置、尺寸、层级、裁剪、图片、文字和间距按同分辨率截图与 diff 对齐。
- 3D 不要求跨引擎逐像素重合，但模型必须出现，职业与部件正确，不得镜像、翻转或角度明显错误；位置和比例大致正常，骨骼常驻特效必须与老端一致。
- 页签被点击不等于页内完成。可见的“更换/激活/升级/确认”必须各自进入控件清单，并跑未激活、可操作、处理中、完成和重开状态。
- 灰显必须使用灰阶材质，不能只降 Alpha。红点必须同时满足下一步配置存在和权威背包材料充足，背包事件到达后立即重算；禁止把全部未激活项标红。
- 接入模型预览时不得删掉原有数据消费者。`FashionMainView` 曾因重构 3D 链误删战力刷新，只有把旧 `FashionCase` 与新视觉用例串行执行才发现。

### 2.5 页面“看起来有列表/弹窗”但结构与身份仍错误

2026-08-04 第4轮再次证明，截图里出现横排条目、点击后出现一个窗，并不能证明与老端一致：

- 时装页曾同时有真实 ScrollRect 和重叠假 Content，Bind 指向假节点。条目能横排，但无 Viewport 裁剪、不能拖动。验收必须同时检查 `ScrollRect→Viewport(RectMask2D)→Content(LayoutGroup+ContentSizeFitter)`，再从可见条目经真实射线做 `BeginDrag/Drag/EndDrag`，验证 Content 位移和末项可达。
- 套装竖牌曾因父容器 x=599、子图右锚 x=-45 叠加而整体右偏。跨父容器比较必须把世界角点反算到页面根左上角；局部 `anchoredPosition` 只用于解释，不是最终位置证据。
- 套装条件格曾继承 `BaseAwardItem` 默认点击，打开通用小物品窗。每个可见格必须作为独立叶子核对具体 View 类型、根尺寸、主题/品质底图、模型/特效和遮罩关闭链；同排一个格子通过不能代验其他格。
- `IllusionTips._img_bg` 在老端 scene 没有 skin，由代码按 `goods.color` 动态赋 `ui_tips_pzbg_1..7`。Unity 只验 Image 尺寸会让透明底图假通过；视觉 ready 必须要求 Sprite 非空、组件启用、未被 Canvas cull，并将七张图放入点击前资源闭包。

## 3. 人物面板功能口径

- 基础属性按老端顺序展示 13 项：攻击、生命、破甲、防御、命中、闪避、暴击、坚韧、元素攻击、元素防御、绝对攻击、绝对防御、移动速度。
- “基础属性/极品属性”按钮必须切换标题和列表；极品属性顺序按老端 `spe_show_index`，百分比值按协议的万分比数据除以 100 后显示 `%`。
- 普通属性显示原始整数，不能用“万/亿”缩写；等级经验与战力可继续使用各自既有格式。
- 已有真实模块的入口直接打开。称号复用 `DsgtModule.prefab` 与 41101 权威列表，名誉复用 `MarriageHonourView` 与 `config_fame_lv`，属性问号复用 `CommonModule.prefab/InstructionView` 并读取 `configinstruction[453]`；世界等级按钮显示当前角色的世界等级数据。尚未迁移的成就、勋章、属性药剂等入口仍必须走统一路由占位提示，不能静默无响应或伪造业务页面。
- 世界等级说明层默认隐藏，由世界等级按钮打开，点击说明底板关闭。

### 3.1 人物窗框与模型重开

- 人物一级页签严格为老端五项：人物、垂神翼影、古法符相、殒锋天刃、玄穹云披。后四项必须按 `configfuncopencondition` 的同名 View 条件显隐，禁止把技能、天赋等二级入口塞进底部页签，也禁止生成无文字空按钮。
- 复用 `BaseWindowSkin/TabButtonTwoSkin` 前必须先检索已验收的同形态消费者。矩形文字页签以 `AchievementFlow` 为基线：只传 `TabSpec.Label`，不得传 `UpImagePath/DownImagePath`；一旦传入图片路径，共享组件会切到图标页签语义并隐藏文字，形成“只有两个小图、没有地境/天境文字”的重复缺陷。目标 Flow 的 CliVerify 必须直接检查其 `TabSpec` 和克隆后的可见文字，不能只检查模板或底图资源存在。
- 天境这类老端 `HBox + 182px` 卡片若转换后的 `Content` 高度仍是 100，`HorizontalLayoutGroup.MiddleLeft` 会把卡片上移 41px，标题落到 `RectMask2D` 外而背景仍部分可见；必须按老端运行树把卡片顶边对齐 viewport 顶边，并在同一页面坐标系断言首屏可见标题不被裁剪、滚出项被裁剪。老端运行时 `HTMLDivElement.fontSize=0` 只是对象快照，不是最终排版事实；要追到 `SetHtmlStyle(f:20)` 等主动样式调用，把字号、单行和溢出语义固化到 Prefab 模板。
- 文字型 UI 粒子不能只验 Handle/Renderer。共享 RT 会做全局横向翻转，转换后的资源若因此出现“月如/称号反向”，应给精确资源 profile 配 `mirrorX`，不得改全局通道。验收保存 RT 两个时点，要求非透明/亮像素和像素差同时达标，并保存最终 Canvas 截图人工核对字序。
- Laya `Sprite/Box` 转换后可能保留 disabled、透明占位 `Image`；页面私有点击助手若优先取到它但不启用，会形成“按钮看得见、实际射线命不中”。容器点击统一使用 `UIUtil.AddClick(Component)`，并以真实 `GraphicRaycaster → PointerClick` 验证命中、门禁提示和未授权写协议零发送。
- 人物页窗底使用老端 `bigBg/ui_role_new_bg_1.jpg`。`EquipmentView/model_bg` 在老端没有皮肤，对应 Unity Prefab 必须同时保持空 Sprite 并禁用 `Image` 组件，让公共窗框背景直接显示；Unity UGUI 的 `Image` 即使 Sprite 为空，只要组件启用且颜色不透明，仍会绘制整块白色矩形。不得只清 Sprite，也不得再放圆形舞台图覆盖顶部模型区。
- `BaseWindowSkinView` 与人物内容会被缓存，但共享 `UIModelStage` 可能被其他页面清空。缓存窗口每次重开都必须重新选择当前页，使 `EquipmentView.OnShow()` 再次装配角色模型；只调用窗框 `Show()` 会造成“第一次有角色、第二次消失”。

### 3.2 角色技能页与动态天赋树

- 当前角色技能清单固定为主动 6 格、被动 6 格、天赋 41 格（攻击 10、防御 10、通用 11、绝对 10）。每格必须作为独立叶子点击并核对具体详情；页签打开、第一格有内容或截图里看见图标都不能代验其余格。
- 运行时从模板克隆 `BaseView` 子页、页签或格子时必须走 `Show()/Hide()`，让 `EnsureBound/OnInit` 完成绑定。只调用 `gameObject.SetActive(true)` 会跳过 `OnInit`，形成可见但无点击监听的静默故障。
- 动态树高度必须写到实际 `ScrollRect.content`。推荐锚点为 `anchorMin=(0,1)`、`anchorMax=(1,1)`、`pivot=(0.5,1)`、`anchoredPosition=0`；全拉伸锚点再写 `sizeDelta.y` 会把父高重复计入。切换类型后停止惯性并回到 `verticalNormalizedPosition=1`，随后强制重建布局。
- 真实拖动要从能被 `GraphicRaycaster` 命中的格子开始；背景同级节点可能截断 ScrollRect 事件。浏览器自动化的拖动路径要跨过多个渲染帧，过短、瞬时的路径可能退化成一次选中点击。
- 老 H5 “绝对”树当前配置的 `lv_data.icon=0`，全黑圆不是 Unity 应复制的目标。确认资源缺失后保留 Unity 真实图标并在台账标记例外；同名、同相对路径资源仍需用文件哈希确认实际内容。
- `21011/21012` 属于写事务。无授权时只能验证前置拦截、确认框和取消；成功提交、权威回包、当前页即时刷新及关闭重开未跑完时，父节点不得 `done`。

### 3.3 称号佩戴与场景名牌

- `dsgt_adorn_button`是佩戴/卸下的唯一真实点击面。41102/41103发送前必须以41101权威列表、`config_dsgt`和服务端绝对过期时间二次校验；它们与41106/41109共用互斥单飞。失败不重查，成功只发一次41101，严禁用ACK的id或本地推演补丁`CurrentUsedId`。
- 41105不是只存raw的旁路通知。主角包更新`RoleModel.MainRole.Figure`，其他玩家包更新`SceneManager`中的RoleVo，然后统一交给唯一场景称号呈现器刷新NameBoard；角色移除、切场景、断线必须释放图和特效实例。
- 老端NameBoard原始缩放为150逻辑宽度，称号按120口径展示，Unity等价缩放固定为`120/150=0.8`。静态称号直接加载配置图片；动态称号必须使用`UIEffectStage`并等待专用相机实际Render，不能把RenderTexture已绑定或加载Task完成当作出帧。
- 场景适配按页面根逻辑坐标居中，不按桌面像素硬编码；720×1280移动端与1920×1080 Web都必须复验。5502星空副本、36001～36999极地/跨服极地和面具态隐藏称号，不能只在初次创建时判断。

### 3.4 人物页职业展示语音

- 老端 `EquipmentView.AddVolce` 在人物装备页展示时按职业播放 `role/boy_show1`、`girl_show1`、`boy_show2`、`girl_show2`；这不是通用按钮点击音。Unity 必须在 `EquipmentView.OnShow` 单独播放，不能因为 `ui/2_dianji` 已响就认为声音完成。
- 播放与模型加载是同一页面演出，但生命周期独立：关闭、切页、Dispose/Destroy 立即停止；声音异步加载期间关闭页面时，后到句柄必须马上停止，禁止静态语音留在场景中。重复收到角色信息只刷新模型/数据，不重复叠播开页语音。
- 当前职业展示音已进入 `PreloadGameStartAsync` 的当前角色小闭包，因此正常游戏内首次打开人物页不再冷加载；不得为此预热其他职业或全部角色语音。

## 4. 设置面板功能口径

- 四滑条读取 10202/10203 的同屏人数、特效数量、音效、音乐；拖动即时影响本地显示/音量，关闭面板时批量上报。
- 自动拾取与屏蔽项按 `config_setting.json` 顺序和默认值生成，点击发 10203；屏蔽页为两列 10 项。
- 坐骑、降神、自动任务按功能开放和服务端设置显隐，隐藏分块必须由布局系统自动收拢。
- 改名、复制 ID、切换角色、返回登录、还原默认、脱离卡死、修复异常、关闭和两个页签均必须有真实点击链。
- “更换头像”不是设置模块内的小弹窗。老端路由是 `OpenFun(203, [DressType.Head])`；Unity 必须使用显式语义路由 `SettingFlow.Close()` 后 `FashionFlow.OpenDress(DressView.HeadType)`，落到外层“装扮”、内层“头像”，禁止再用会与外层页签混淆的数字索引。
- 当前装扮页必须覆盖外层时装/发饰/装扮/套装，内层气泡/相框/头像，列表条目、预览、属性、材料、2/5/10级技能圆标与技能详情。R623已按本轮产品授权恢复11201/02/03/05：激活/升级必须双次校验配置与背包材料，使用/卸下只允许玩家显式点击，同页互斥单飞，成功按权威回包即时刷新、失败保旧；11204其他玩家场景广播仍禁止接入。
- 改名验收不得停在 42602 资格弹窗。提交成功后，当前设置面板上的角色名必须立即刷新，重开后仍与权威 RoleModel/服务状态一致。
- 改名输入按老端宽度口径校验：ASCII计1、其他字符计2，长度4～12；提交前做本地敏感词检查，42604资格失败、42601事务失败、取消确认和关闭页面都必须释放单飞锁。
- 用户协议和隐私政策必须在登录Prefab已释放的正常游戏态仍可独立打开、切文档和关闭；只在登录流程里可用不算设置功能完成。
- 头像、完整按钮、分区标题纹、底部五钮、页签必须使用 setting 目录的老端原图，不得用同名占位图替代。

## 5. 生成与验收

- `SettingModule.prefab`、`DressModule.prefab`和`FashionModule.prefab`均已进入精修期，是后续位置、尺寸、图片、字号、颜色、间距和布局的唯一事实源。设置Creator及Dress/Fashion升级器已退出自动重建注册表；它们只保留显式灾难恢复/旧产物迁移入口，验收用例禁止先执行生成器。
- 后续视觉修改应直接改对应Prefab；功能代码只绑定既有节点、更新数据、事件、协议和必要显隐。确需新增视觉锚点时，在当前Prefab上做一次幂等增量补丁并立即把结果落袋，不能复制整页、重转模块或让运行时代码重新建树。
- `RoleModule.prefab`同样已由人工接管，人物页专用`RoleEquipmentCreator`已移除生成逻辑并退出重建注册表（同名空壳只兼容已有Unity工程文件）。
- 静态验收至少核对：根尺寸、顶部/底部/页签坐标、Grid/VerticalLayout 组件、标题默认显隐、PNG 实际内容。
- 运行态验收必须经过真实 Prefab 的 `Show()`，分别截图设置基础页、设置屏蔽页和人物页；仅看 Scene/Prefab 预览不算通过。
- 从主界面进入设置也属于验收链。设置/好友/商城固定入口必须把点击语义绑定到玩家实际命中的 `_img_setting/_img_friend/_img_shop` 可见 `Graphic`，并走 `GraphicRaycaster→PointerClick`；只给外层 `_box_*` 补透明 Button 不能证明 WebGL 可点击。
- 设置→头像分支还必须通过真实射线依次点击四个外层页签、三个内层页签、头像条目、技能图标和技能详情关闭；同时记录 cold/warm 时间，并断言资源目录没有新增文件、受限协议没有发送。只断言目标 View 已打开不算通过。
- 重点回归 720×1280 与真机长宽比，确认分块显隐、两列列表、按钮命中和弹窗层级不会随分辨率漂移。

### 5.1 低成本整树回归

- 设置固定路线使用54节点台账，其中46个叶子；每批结果只写实际跑过的叶子，再由`route_ledger.py apply`回卷父状态，避免人工反复维护长表。
- 多个CLI用例应合进同一个`SettingsFullSuite`顺序执行，复用一次Unity启动、配置缓存和导入状态。最终批次依次跑`Dress/SettingFullRoute/SettingFashionCurrent/Fashion/SettingPk/ProtocolCoverage`，总判定`pass=True`。
- `CliVerify.Run`会在用例结束后主动退出Editor，命令行不要再传`-quit`。代码变更触发域重载时，`-quit`可能让Editor在`executeMethod`之前以0退出；日志没有业务`VERDICT`就不算执行过。
- 第3轮头像链最终实测冷开1867ms、热开71ms，打开前后`addedResources=none`。冷开三份Prefab并行加载；热开复用实例。首次运行临时补资源或只记录“第二次快”仍判失败。

### 5.3 第4轮新增硬闸

- `target_identity`：实际 View 类型、根尺寸、主底图实绘和遮罩链。
- `layout_structure`：滚动容器树完整，不能用平铺节点冒充列表。
- `scroll_interaction`：从 GraphicRaycaster 命中后真实拖动，Content 位移且末项可达。
- `page_space_geometry`：关键 Rect 输出页面根坐标；局部锚点不同可以等价，局部数字相同也可能屏幕偏移。
- `render_completion`：RT 已绑定不等于画面已经出帧；必须等待专用相机实际 Render 完成，并用非透明像素数证明模型真实进入截图。
- 动态文案要按配置字段语义拆到正确容器，记录各组矩形、preferred height、相邻组不重叠和背景包围盒。不要用固定高度掩盖换行差异。
- 最终截图目录每轮只写一次；图片查看器已映射的 PNG 不原地覆盖，避免 Windows 1224 错误后继续拿旧图验收。

### 5.2 视觉与资源闸

- `type=page` 的台账节点必须带 `control_inventory[]`，每个可见、状态和条件控件映射到一个直接子节点。截图出现清单外控件时先回卷父状态，不能沿用历史 `done`。
- 资源型首屏在约350ms、1000ms和最终ready分别取证；占位图、粉块或旧选中项残影不算ready。View应暴露可判定就绪状态，禁止用固定等待掩盖冷开问题。
- 预检必须连续跑两次。第二次要求`imported=0、configured=0`；玩家点击前后资源目录必须零新增。只把导入挪到计时前、但每轮仍重导，不算优化完成。
- 第3轮时装闭包为712项、装扮闭包为154项；第4轮加入`ConfigIllusionModel`和七张品质底图后，时装闭包为720项，第二次预检`imported=0/configured=0/added=0/missing=0`，四格点击后`addedResources=none`。第4轮最终截图见`output/settings_fashion_round4_delivery/`。

## 6. 切换账号/角色黑屏排障

- 症状：设置页点击“切换账号”或“切换角色”，确认后游戏场景被清理，但没有登录页或选角页，只剩黑屏。
- 根因：正常进场后登录模块为节省内存已释放全部 Prefab；旧退出流程只调用 `ShowLogin()` 或等待角色列表回调，没有重建登录舞台和页面。
- 正确顺序：双按钮确认弹窗 → 清除游戏内自动重连状态 → 断线并完成业务 UI/场景 teardown → 重建登录模块。切账号显示登录页；切角色显示等待层、重连当前服、发送 `10000`，再由权威角色列表打开选角页。
- 快速检查：断线后日志必须先出现登录 Prefab 重新加载，再出现登录页或“正在返回角色选择界面”；不得只看到 MainUI/Scene 释放日志。重复切换时还要确认事件只触发一次。

## 7. 角色 UI 两日复盘：质量门槛正确，但生产顺序失衡

> 本节记录 2026-08-04～2026-08-05 角色技能、称号分支精修的吞吐复盘。以下“优化候选”用于后续讨论，尚不替代现行 UI 对接/精修流程与最终验收硬闸。

### 7.1 结果与成本不匹配

- 从用户可见产出来看，两天主要交付角色技能页和称号分支，速度不能接受。虽然技能页实际包含主动 6 格、被动 6 格、天赋 41 格，称号还包含列表、详情、佩戴和场景表现，但内部复杂度不能代替可见交付速度。
- 角色路线最终有 117 个节点，状态仅为 72 `done`、4 `blocked`、30 `not-run`、11 `baseline-only`；说明工作量很大，但整页仍未收口。
- 本轮正式提交涉及 292 个文件，正式证据约 168 份，提交体积约 171.8 MB；另曾产生约 1398 个失败或中间证据文件和约 1.47 GB 临时内容。大量时间花在验证产物、目录清理和 Git 收口，而不是用户可见页面。

### 7.2 主要根因

1. **Web 基础设施与页面制作混为一项任务。** 旧版本 Web、Addressables/catalog 不匹配、`boot_config.json`、CDN 路径、90% 卡加载、缓存和宽屏适配等问题必须修，但它们是公共基础任务，不应继续计入单页制作吞吐。
2. **过早按最终验收粒度执行。** 页面公共结构和共享运行时根因尚未稳定，就开始逐格、逐状态、逐分辨率留最终证据；后续发现动态克隆页签没有走 `Show/OnInit`、高度没有写到真实 `ScrollRect.content` 后，前面的多轮验证自然失效。
3. **构建、运行和截图循环过密。** 小改动后反复跑 CLI、Web、重进、拖动和截图，验证批次太小；重复运行次数增长，却没有同比增加新的诊断信息。
4. **证据策略没有分层。** 相同结构的 53 个格子仍承担接近独立截图的成本，失败截图和中间目录也长期堆积。最终验收需要逐叶结论，但不等于每个同构叶子都必须重复保存同等级图片证据。
5. **隔离和 Git 收口成本过重。** 当时为保护现场创建了独立 worktree/Library，随后承担大仓检出、资源状态、合并冲突、临时服务器占目录和清理成本。当前项目规则已修正为原地最小修改优先；只有确认无法安全原地完成且用户同意后才隔离。
6. **机械工作占用高成本模型。** 清单展开、重复映射、证据索引、批量断言、日志搬运和 Git 清理消耗了大量 token；主模型没有把主要额度集中在共享根因、视觉判断和交互语义上。
7. **缺少明确止损线。** 当 Web 基建、证据整理或同一根因连续重跑开始主导耗时时，没有立即拆单或暂停扩展，导致“内部工作很多、页面进展很少”。

### 7.3 必须保留的质量门槛

- 老 H5 与 Unity 仍以同账号、同路径、同 viewport、有效登录会话的真实运行态顺序对照；Web 壳与 Addressables 内容必须同批匹配。
- 移动端是主目标，必须完整验核心路径；Web 宽屏至少覆盖全屏遮罩、缩放、裁剪、关键交互和代表状态。
- 真实 `GraphicRaycaster→PointerClick`、真实滚动、动态克隆 `Show/OnInit`、实际 `ScrollRect.content`、关闭重开和即时状态刷新不能降级为静态对象检查。
- 3D/特效仍以专用相机实际 Render 和有效像素为准；Renderer、Task 或 RenderTexture 存在不能代替真实出帧。
- 写事务仍须覆盖提交、成败回包、父页即时刷新和重开；未授权或无法安全恢复的写入继续标 `blocked`。

### 7.4 下一版流程的讨论候选

1. **基础门禁独立计时。** 开始页面前用 15～30 分钟固定小样本确认老端、Unity Web、账号、viewport、壳/catalog、缓存和加载链。未通过就单列“Web 基础任务”，修通后再开始计算页面工时。
2. **先修共享根，再扩叶子。** 每页先完成公共 Prefab、布局、初始化、数据绑定和一条代表路径；代表路径稳定后，才批量处理同构控件。共享根因连续两轮仍不稳定时，停止扩展叶子。
3. **生产验收与最终验收分层。** 生产阶段保留页面级基线、状态类别代表截图和机器断言；只给独特叶子、差异项和缺陷留独立截图。页面结构稳定后，再执行完整逐叶审计和最终 Web 回归。
4. **按修改面批量验证。** 同一结构或同一数据映射合成一个修改批次；静态/编译在批次内先过，CLI 按功能批次跑，Web 按稳定页面或里程碑跑，不在每个小修后完整打包。
5. **按价值分配模型。** 主模型负责范围裁决、共享根因、视觉/交互判断和最终复核；确定、机械、可核验的清单生成、批量修改、断言和证据索引优先交给 Luna 或确定性脚本。
6. **先交付可见增量。** 每 60～90 分钟至少应形成一个用户可直接看到、可运行的页面增量，并汇报完成项、阻塞项和下一批；不得等整棵路线和全部证据归档后才展示结果。

建议先以以下止损线试运行，再根据两到三个页面的数据调整：简单页 1～2 小时，中等页半天，复杂页 1 天；超过目标 1.5 倍必须暂停扩展并报告根因。环境、台账、证据和 Git 处理合计超过本批次 25%，或同一问题无新信息地重复验证超过 3 次时，必须拆单、压缩证据或回到共享根因诊断。

### 7.5 真实 Web 对比与打包结论

- 角色精修的主对比链固定为“老 H5 真实页面 → 确认断线 → 同账号 Unity WebGL 真实页面”，由后台 Headless Playwright/Puppeteer 操作固定 viewport 并生成 old/unity/overlay/diff；Computer Use 和 CLI 合成截图不再承担日常主视觉证据。
- 对比脚本必须先核对当前 Git commit、dirty 指纹、Player 哈希和 catalog 哈希。旧包、壳与内容不同批、缺少 `boot_config`/CDN 覆盖或页面仍指向旧 catalog 时直接失败，不继续截图。
- Headless 对比不能消除 WebGL 构建时间。首次基线或内容状态不可信时完整构建内容+壳；修改 C# 后重打壳，纯 Addressable Prefab/图片/配置改动在已验证基线上只打内容。当前壳预算仍按 12～25 分钟，不能把“增量”误解为 C# 修改也能几分钟热更。
- 页面开发先在真实 Prefab/CLI 中批量解决确定性问题，再按页面或逻辑批次构建真实 Web。复杂页面通常控制在 1～2 次壳构建；第一次 Web 对比后的纯视觉尾项走内容更新，发现 C# 问题则集中修完再进行第二次壳构建。
- 角色界面目标粒度没有问题：完整页面内的所有控件和叶子仍须做完。需要优化的是同构实现、证据去重、通用自动化和推进顺序；不得再用“页面内部叶子很多”解释三天只有两个页面的低吞吐。
