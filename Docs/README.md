## 三、什么情况下必须更新文档

满足任意一项，就必须在本轮更新或新建仓库内文档：

1. 新增或改变架构、框架、公共组件、共享服务或跨模块约定。
2. 新增或改变 Editor 工具、资源导入/转换、Addressables、构建或发布流程。
3. 改变协议语义、登录、进游戏、主界面、场景等关键链路。
4. 修复经过多轮定位、根因可复用、表现无规律或后续高概率复发的问题。
5. 引入新的配置资产、人工操作步骤、Unity 菜单或特殊验收方法。
6. 里程碑、范围、风险、blocker 或完成状态发生变化。

纯错字、格式整理、无行为变化的机械重命名可以不更新专题文档，但最终报告必须说明为什么不触发文档更新。

## 四、写到哪里

| 内容 | 位置 |
|---|---|
| 系统设计、数据流、生命周期、边界 | 更新现有专题文档；没有则新建 `Docs/{模块}-{主题}.md` |
| 可复用故障、根因、证据和避坑 | 相关专题的“经验/排障”章节，或 `Docs/{主题}-经验与排障.md` |
| 编码和目录约定 | `Docs/Shenxiao编码规范.md` |
| 所有 AI 必须遵守的项目硬规则 | 根目录 `AGENTS.md` |
| 已验证进度、范围变化、风险 | `Docs/Shenxiao实施进度.md` |
| 操作人员执行步骤 | 对应 SOP、手册或 Runbook |
| 临时证据 | `output/` 或专项报告；结论仍需回写正式文档 |

外部 AI memory 可以帮助检索历史，但不能成为唯一信息源；会影响后续实现和验收的结论必须回写仓库。

## 五、文档最低质量

技术文档至少包含：

1. 背景和要解决的问题。
2. 最终方案与关键数据流。
3. 适用范围、边界和明确不做的内容。
4. 关键代码、资源、配置和入口路径。
5. 操作或迁移步骤。
6. 验证方法、通过标准和已知风险。

经验文档至少包含：

1. 用户可见症状。
2. 最终根因及排除过的错误方向。
3. 代码、日志、截图或老端源码证据。
4. 正确处理方法。
5. 后续禁止做法和快速排查顺序。

不要直接粘贴聊天记录，不写“应该没问题”一类无法验证的结论。文档应说明当前事实，而不是复述修改过程。

## 六、提交前文档闸门

每次提交前完成以下判断：

- 本次是否命中第三节任一条件？
- 命中时，是否已更新专题文档、经验和实施进度？
- 新文档是否已加入本索引？
- 新决策是否需要同步进 `AGENTS.md` 或编码规范？
- 文档写的是已验证事实，还是未经验证的推测？

文档与对应实现应放在同一提交中，避免代码已经改变而说明长期滞后。
