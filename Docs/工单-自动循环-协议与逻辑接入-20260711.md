**死活判定必须三层,缺一层就会误判**(轮21 血训,见进度日志):①老端有无非注释 handler;②**服务端有无 `pt_XXX:write(号,..)` 的真实调用点**;③服务端族级路由是否 LIVE。轮21 审计只做了第①层,把 `40505`/`40507`/`46030` 三个**服务端死号**误判成"未申报的活缺口"并写进 spec 派了下去,靠实现代理回 Erlang 原文才拦下。

**⭐第4层判定:老端 UI 可达性**(轮22 立,2026-07-19)。三层协议判定全部为"活"(handle 非注释 + 有真实 write 调用点 + 族路由 Live)不等于该号该做——如果**老端玩家在真实客户端里实际摸不到触发它的入口**,这个"活"就是纯服务端设计稿状态,Unity 不应该照抄。三个判据(占其一即可判定不可达):
  - **view class 不存在**:老端最终要打开的 view/窗口类,在 `h5/src` 源码与 `cdn/js/bundle.js` 编译产物里都搜不到定义(`window[view_name]` 恒 `undefined`,`new view_class()` 会直接抛异常)。
  - **入口配置不渲染**:触发按钮依赖的配置表(如 `main_func`)里没有对应的 id/开关项,按钮本身在 UI 里就不会被创建出来。
  - **发送点/事件订阅零**:协议号唯一的触发路径本身是死的(唯一入口函数体整段注释,或事件 Fire 出去后全仓库无任何 `.Bind` 订阅方接收)。
  这一层不推翻三层协议死活判定本身,只改变"该不该移植"的结论:按**事实源=老端客户端**原则,判定为不可达的号一律**不移植**,killlist reason 用 `old_client_unreachable`(与"服务端从未 write/进程未起"的传统死号 `dead_server_*` 系列区分开,证据链要给"摸不到"的三件套,不是"服务端不回包"）。另有一类**服务端设计完整、但老端从未做出对应 UI/交互**(全仓库 zero 引用,连老端自己都没接)的孤儿协议,reason 用 `old_client_never_wired`。
  先例:工单 #14 守卫公会本(2026-07-13 立,当时就是按这一层裁的,只是没起名字)、`24011` 组队委任队长(三层协议活但 `ShowPlayerMenu` 老端入口已空)、轮22 公会探索 `40050-40058`+捐献链 `40024/25/26/41`(9+4=13 号,`GuildExploreBaseView` 等 view class 全不存在 + `main_func` 无对应 id,轮21 审计曾把这批的"未申报"定性为"严重虚标",轮22 三层复核后确认 0 个需要实现,见工单 #13c)。
