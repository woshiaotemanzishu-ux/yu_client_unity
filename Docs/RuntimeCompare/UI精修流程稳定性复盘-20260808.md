# UI 精修流程稳定性复盘（2026-08-08）

> 范围：`audit-game-ui-route` 的路线建账、结果回填、证据合同、真实 Web 收口及历史共鸣更新器
>
> 本轮性质：流程/工具修复。没有启动或控制 Unity，没有切换构建平台，没有运行玩家账号事务，也没有生成新的页面运行态结论。
>
> 结论：现有流程的方向正确，人工复查也证明效果可接受；不稳定主要来自“文字规则已升级、机器执行器仍可绕过”。本轮已补齐 schema 6、原子 apply、运行批次/哈希证据、动态特效结构合同、根页 Web 指纹，并封存会覆盖新证据的历史共鸣更新器。

## 一、审计到的实际缺口

### 1. 空闸可以假完成

旧 `route_ledger.py` 允许完成叶显式写 `applicable_gates=[]`。验证器只遍历数组内容，因此没有任何门禁也能返回通过。文档虽写“不适用项要显式移除并说明”，脚本没有执行这条规则。

### 2. apply 不是事务

旧 `apply` 的顺序是“合并 → 写正式文件 → validate”。结果里有未知 ID、缺证据、错误父状态或坏 gate 时，命令虽返回失败，正式台账已经被改过。重新执行又可能基于污染后的状态继续传播。

### 3. 证据与运行批次没有绑定

旧 schema 只要求若干字段是非空字符串。`effect_evidence=["effect-diff.png"]` 即可通过，脚本不知道文件是否存在、是否已被覆盖、是不是同一 Handle 的两个时间点，也不知道当前 Git/Player/catalog 是否与截图同批。用户此前发现的静态流光、滚出残框、错误弹窗和透明底图，正是这类“路径非空但语义不成立”的假绿。

### 4. 缺陷重开仍可能复用旧绿灯

节点从 `done` 降为 `defect/needs-runtime-verify` 时，旧 `gates=true` 和证据字段仍保留。后续结果只改回 `status=done`，即可继承旧证据；没有“哪几个闸被新截图作废”和“本次重新验证属于哪个 run”的机器边界。

### 5. 页面完成没有同批 Web 机器闸

项目规则要求页面 `done` 保存 Git commit、dirty 指纹、Player/catalog 哈希和 Headless 对比报告，但旧台账没有根页级绑定。Editor/CLI 叶全部完成时，父页可能自动变绿，即使没有真实 WebGL 同账号顺序复走。

更隐蔽的一层是：叶子被新截图打回后，旧根页 `route_run_id` 若继续残留，后续只补 Editor 叶证据也可能自动复用旧 Web 批次重新收口。

### 6. 共鸣路线的 schema 与写入口漂移

仓库文档和经验写“共鸣使用 schema 5”，实际 458 节点正式账仍为 schema 4。`Tools/Conversion/update_resonance_route_ledger.cjs` 硬编码只接受 schema 4，并在每次运行时先对 458 个节点执行 `setDone`，再重开当时已知的缺陷。未来若出现新的用户证据，重跑该脚本会把未写进脚本的后续作废结论恢复成旧绿灯。

### 7. 现存台账并非全部可校验

审计 12 份已跟踪的 `output/ui_route_audit/**/route-ledger.json`：schema 分布为 1 份 schema 2、9 份 schema 4、2 份 schema 5。修改前的挂机“提升”扫光台账只有节点树，没有任何 `status`，通用校验实际报 4 个 `invalid status None`；对应 `results.json` 还使用了未注册的 `reopen_consistency` 和对象型旧 `effect_evidence`，说明结果从未由正式 apply 收口。

### 8. 原子替换仍可能并发丢更新

文件级 `os.replace` 只能保证不会读到半份 JSON。若两个流程同时读取同一份旧账，各自合并后依次替换，后写者仍会静默覆盖前一批结果；旧 `init` 也允许直接覆盖已经存在的正式账。这不是格式损坏，却会造成状态偶发倒退，尤其难从最终文件判断。

### 9. manifest 与正式账没有持续绑定

旧 init 虽把 manifest 路径和哈希写入账本，validator 却不读取、不比对。manifest 后来新增条件控件、调整父子关系，或账本被手工改树时，旧完成态仍可能继续通过，无法判断证据对应的是哪一版路线拓扑。

## 二、本轮已修复

### 1. schema 6 与兼容边界

- `route_ledger.py init` 现在固定创建 schema 6。
- schema 2～5 继续按历史规则读取，不原地抬版本，不伪造新证据。
- schema 5 的完成叶至少禁止空 `applicable_gates`。
- schema 6 manifest 必须恰好一个 `page` 根、父链无环、类型/风险合法；页面控件清单与全部直接子节点一一对应，漏项或多个控件共用笼统子节点会在 init 阶段失败。
- `manifest_source` 现在作为不可变拓扑合同校验实际文件哈希、路线名、节点集合及 `parent/type/risk/control_inventory`；拓扑变化必须创建新版本账，旧完成态不能跨树复用。

### 2. 原子 init/apply

- `init` 与 `apply` 均先构造内存候选并完整校验，再用同目录临时文件 + `os.replace` 原子替换。
- `init` 现在拒绝覆盖已存在目标；同一绝对台账路径的 `init/apply` 使用系统临时目录中的非阻塞跨进程锁，并发第二写者明确失败，需读取最新账后重放本批 results。
- 现有台账本身无效时，`apply` 直接拒绝。
- 候选失败时正式文件逐字节不变；故障注入已验证。
- `summary.total/status_counts` 由工具重算，schema 6 会拒绝手写汇总漂移。

### 3. 每闸绑定 run 与证据

schema 6 完成叶的每个适用闸都必须有：

- `gates[gate]=true`；
- `gate_runs[gate]=verification_run_id`；
- `gate_evidence[gate]=[...]`；
- 对应专项结构字段。

完成结果必须在本批 results 中显式刷新全部适用闸，且三张 gate 表的键必须与 `applicable_gates` 完全一致；重新完成时整体替换旧表并清除已不适用的专项字段，不能靠节点残留数据恢复 `done`。文件证据记录路径与 SHA-256，校验器会实际读取并比对；人工断言必须写来源、带时区时间和精确覆盖范围。

### 4. 新证据精确作废

结果可写 `invalidate_gates/invalidation_reason/observed_at`。工具会：

1. 将被作废闸的旧 run/evidence 归档到 `evidence_history`；
2. 将 gate 置 false 并清理对应专项字段；
3. 自动回卷父状态。

已完成叶直接降级但未给出具体闸时，默认作废该叶全部适用闸，避免旧绿灯残留。

### 5. 结构化高风险证据

- `timing` 分开记录 cold/warm 的 first-visible 与 interactive-ready。
- `visual_match` 固定 old/unity/overlay/diff 四份带哈希文件，且只能绑定 real-Web run。
- 弹窗身份、滚动容器、真实拖动、页面根矩形、模型存在/朝向/部件/特效、RT 实际像素、资源二次幂等均有结构化字段。
- 动态特效固定记录所有者、老端七项调用参数、动画属性 → 材质属性 → Shader 分支、同一 Handle 双帧/时间/像素差/alpha 包围盒、隐藏/重开；滚动宿主再要求 full/partial/hidden 三态且 hidden alpha=0。
- 共享组件固定记录 GUID/实例链、全部直接消费者、使用形态分组、每组代表样本及状态矩阵；每个消费者必须恰好进入一个分组，根或生命周期变化必须包含高频既有页面。

### 6. 根页真实 Web 同批闸

根页面 `done` 必须以 `route_run_id` 指向 `environment=real-web` 的 run。该 run 同时保存：

- Git commit 与 dirty SHA-256；
- Player 与 catalog SHA-256；
- `720×1280` 和 `1920×1080`；
- 老端已断线、Unity 会话有效；
- 带 SHA-256 的 Headless 报告。

根页一旦回卷为非完成态，工具会清除旧 `route_run_id`。重新收口的 Web run 必须不早于所有完成叶引用的 run，并与它们保持相同 Git/dirty 指纹；这样新 Editor 修复不能借旧 Web 包背书，Editor、CLI、用户局部确认与真实 Web 页面收口在机器层明确分开。

### 7. 共鸣历史更新器封存

`update_resonance_route_ledger.cjs` 默认立即退出并说明它只是 2026-08-07 历史重放。只有显式传：

```powershell
node Tools/Conversion/update_resonance_route_ledger.cjs --legacy-replay --output <candidate.json>
```

才会生成独立候选；候选路径不得是正式 `route-ledger.json`，写完还会调用通用 validator。当前结果统一写 results 并走 `route_ledger.py apply`。

正式路径保护按 Windows 大小写归一化，并在候选已存在时比对文件身份，避免用路径大小写或硬链接别名绕过保护。

### 8. 修正挂机扫光历史台账

挂机“提升”扫光路线已从 4 个无状态节点修正为 5 节点可校验 schema 4 历史账：

- 双时间点动态像素与生命周期两叶保留 `done`；
- 新增真实 Web/资源幂等叶并标 `needs-runtime-verify`；
- 两级父页均据此保持 `needs-runtime-verify`；
- 没有把 2026-08-04 Editor 结果扩大成部署后完成。

## 三、历史台账迁移策略

1. 历史 schema 2～5 文件保持原证据和原完成边界，不批量改写。
2. 下一次真实复验从已有 manifest 运行 `init` 创建新的 schema 6 文件；不要覆盖历史账。
3. 仍有效的历史结论只有在新 results 中显式绑定 run、哈希证据和专项字段后才能进入新账。
4. 共鸣 `route-manifest.json` 已用新 init 做过离线试建：458 节点 schema 6、全 `not-run`、结构校验通过；本轮未把它写成正式当前账，避免在没有新运行证据时制造一次“机械迁移”。

## 四、当前仍未完成的运行态边界

- 共鸣历史账仍是 `done=264 / blocked=80 / needs-runtime-verify=114` 的 schema 4 快照；修后共享根、材料居中、详情布局和完整代表宿主运行态没有因本轮工具修复而自动完成。
- 共享物品呈现 schema 5 专项仍为 5/5 `needs-runtime-verify`。用户已确认的只有品质流光持续运动和完全滚出无残框两个具体缺陷；普通详情、装备详情、其它代表宿主、自动双帧和真实 Web 同批证据仍未补。
- 挂机“提升”扫光保留 Editor 双帧与生命周期事实，但真实 Web same-build、Web cold/warm 和两次资源幂等仍待验。
- 15221/15222 等真实资产事务仍需本轮明确账号/可消耗授权；本轮没有改变任何账号资产。
