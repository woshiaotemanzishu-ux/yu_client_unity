## 5. 本轮暴露出的流程问题

### 5.1 选功能前没有做“当前事实合并”

历史第 1 轮清单、旧机器账、后续专项文档、当前代码和用户最新确认分散存在。若直接把最早的 `not-run` 当成当前状态，会把已经完成的“属性说明”再次选中。本轮以后选叶子的前置闸固定为：

1. 用户本轮明确确认；
2. 当前代码、Prefab、配置与真实运行证据；
3. 当前有效 schema 6 路线账；
4. 专项文档和实施进度；
5. 历史账/早期计划只作为线索，不作为当前完成状态。

冲突时不静默覆盖，要在路线清单追加“哪条旧结论被什么新证据替代”。

### 5.2 “做过”没有拆成稳定状态

同一个入口至少要区分：`placeholder`、`implemented-needs-runtime`、`read-done-write-blocked`、`done`。仅记录“已做”或“未做”会让下一轮无法判断该继续实现、复验还是跳过。本轮成就是 `implemented-needs-runtime + write-blocked`，不是 `done`；属性说明按用户确认和现有实现视为已完成，不再重复开发。

### 5.3 控件清单把事务压成一个叶子

v1 只记录“阶段领取”和“条目领取”两个事务叶，漏掉背包容量、满包确认/取消、升级成功特效和领奖飞图。这样即使按钮发包正确，也会漏验失败前置和成功后视觉。v2 已把这些状态拆成独立语义叶；以后控件清单必须同时枚举条件显隐块、失败前置、确认弹窗、成功演出和返回链。

### 5.4 实现完成与路线验收被混用

离线编译、静态闭包和老 H5 基线可以证明实现方向与资源闭包，但不能证明当前 Unity 玩家可见像素，更不能替代真实写事务、即时刷新和 real-Web。最终交接必须分别报告“实现完成”“离线验证通过”“Unity 待验”“写事务 blocked”“整页 done/未 done”，不能用一个“完成”覆盖五种边界。

### 5.5 子功能记录没有同步回父级当前状态

此前有初始角色路线树，也有技能、时装、称号、共鸣等后续专项记录，但专项推进后没有把状态同步回同一张“人物当前状态”表；下一轮若只读初始树，就会把历史 `not-run` 误当现状。后续每个角色子功能发生状态变化时，必须在同一轮同步三处：专项 schema 6 台账、专项说明/证据边界、角色父级当前状态表。三处都写明状态枚举、观察日期和证据入口；旧历史保留但不得继续充当当前状态。任一处未同步，本轮只能报告实现结果，不能视为完成交接。

### 9.2 当前粒子表现问题

新图明确显示：奖励飞行的数量、大小和方向已经基本正确，错误集中在颜色与透明度——老端是带透明边缘的绿色玉片/光圈，Unity 把透明区域显示成灰色实心圆片。因此缓存源/显示副本拓扑降级为次要门禁，不再作为当前表现问题根因。

确定链路如下：

1. `ui_bangyu_1/2` 的 `lyz_glow_134.png` 为 128×128 RGBA；8255 个 `alpha=0` 像素全部仍保存非黑灰色 RGB，角点约为 `(78,77,78,0)`。
2. 资源内覆盖子材质使用 `Src=One/Dst=Zero`，会把这批 RGB/Alpha 写入 ARGB32 离屏 RT。
3. 所有 `UIEffectStage` 通道最终共用 `UIEffectAdditive.shader`。该 shader 不使用 RT 原始 alpha，而用 `max(r,g,b)` 作为新 alpha，再以 `Blend One OneMinusSrcAlpha` 贴回 Canvas。
4. 因此本来 `alpha=0` 的灰 RGB 被重新解释为约 0.31 覆盖度，形成截图中的灰色圆片；这与数量、大小、方向无关。

主界面顶部 `ui_zhujiemianzhuanquan` 同样走 `UIEffectStage → UIEffectAdditive`，因此属于同一风险链；底部“变强”看着正常，只能说明某些资源恰好适配该亮度覆盖近似。游戏中的升级、跑动、技能属于场景特效链，不经过最终 RawImage 合成，所以正常并不反驳当前诊断。用户报告顶部效果在 WebGL 更明显；当前可确认的是它共享同一错误合成前提，Web 平台究竟由 RT 色彩空间还是 shader 精度进一步放大，仍需同批 Web 的原始 RT/最终 Canvas 双证据后才能定论。
